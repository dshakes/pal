# ADR 0057 — A2A protocol v0.3: spec card, JSON-RPC tasks, outbound client

- Status: Accepted
- Date: 2026-10-31
- Scope: control-plane `internal/handlers/{a2a,a2a_jsonrpc,a2a_client,tool_catalog,workflow_tools,rest,loop_agent}.go`, routes in `cmd/server/main.go`, SDKs (`a2a` namespace), CLI `pal a2a`, docs `site/.../build/a2a.mdx`
- Plan: AGENT-LIFECYCLE-PLAN Phase 2; builds on ADR 0055 (agent identity, tokens, a2aTargets/a2aInbound policy)
- No migration.

## Context

PAL's A2A surface was a PAL-specific card (`capabilities` as a string list, an
`endpoint`, custom `auth`) plus a REST `POST /a2a/invoke` that blocked up to 60 s.
No A2A client — the reference SDKs, the TCK, other platforms — could talk to it,
and a PAL agent had no way to call a remote A2A agent.

## Decision

### Server: conform to A2A v0.3.0 over JSON-RPC 2.0

- **Card.** `GET /v1/agents/{name}/a2a/.well-known/agent-card.json` serves a spec
  `AgentCard` (`protocolVersion: "0.3.0"`, `preferredTransport: "JSONRPC"`, `url`
  = the JSON-RPC endpoint, skills from the agent's declared `capabilities` label,
  or the agent itself as one skill). A reference client resolves it from the base
  URL `/v1/agents/{name}/a2a`. Visibility rules are unchanged: is_public, or owned
  by the caller; anything else 404.
- **Domain card.** `/.well-known/agent-card.json` is one agent per the spec, and a
  PAL deployment hosts many, so it serves `PAL_A2A_DEFAULT_AGENT` (must be public)
  and 404s otherwise. `/.well-known/agent.json` keeps the legacy PAL directory
  shape so existing consumers do not break. It is not a spec card, and
  spec clients use the per-agent paths.
- **securitySchemes.** `palBearer` (HTTP bearer: PAL session JWT or API key with
  `runs:execute`) and `palAgentToken` (apiKey in `X-Pal-Agent-Token`, ADR 0055;
  the description names the audience SPIFFE id and JWKS URL). `security` lists
  either.
- **Transport.** `POST /v1/agents/{name}/a2a`: `message/send`, `message/stream`
  (SSE), `tasks/get` (with `historyLength`), `tasks/cancel`, `tasks/resubscribe`.
  The `tasks/pushNotificationConfig/*` methods return -32003, and
  `agent/getAuthenticatedExtendedCard` returns -32007. Errors use the spec codes.
  Streaming methods send their errors as an SSE event.
- **A task is a run.** Task id = run id. message/send creates the run through
  `RunService.CreateRun` (trigger_kind `a2a`) on the target tenant and hands it to
  the inline executor. tasks/cancel goes through `RunService.CancelRun`. This code
  writes no run progress, so the executor stays the only writer (invariant #2).
  The A2A view (`contextId`, `messageId`, caller principal, the original message)
  lives in `runs.trigger_meta.a2a`, so no new table is needed. State map: queued→submitted,
  running/paused/waiting→working, succeeded→completed, failed→failed,
  cancelled→canceled.
  `RunService.CancelRun` cancels queued/running/paused runs only. A run parked
  on an approval node (`waiting`) reports `working` but answers -32002 to
  tasks/cancel. Making `waiting` cancellable would need the approval wait to
  observe the cancel, which is a separate change.
- **message/send is non-blocking unless `configuration.blocking: true`.** This is the
  spec wording ("if true, the client will wait"). A blocking wait is bounded at
  60 s. After that the task is returned in its current state.
- **Push notifications are not offered** (`capabilities.pushNotifications: false`).
  The callbackUrl machinery cannot be reused as-is: it has a different payload,
  and A2A needs per-task config CRUD (set/get/list/delete), which means storage.
  That is a follow-up if a customer needs it.
- **Multi-turn continuation is not supported.** PAL runs never enter
  `input-required`, so there is nothing to continue. A message carrying an
  existing `taskId` gets -32004, and an unknown one gets -32001. Terminal tasks
  cannot take messages per the spec. This is the one known TCK deviation (see
  verification).

### Authorization (unchanged rules, now shared)

`authorizeA2ACall` is the old `/a2a/invoke` gate extracted, so both transports run
the same code. The caller is an agent token (audience = target SPIFFE id) or a
human/API key. Resolution goes own-tenant first, then is_public, else 404, and a forged
tenant claim on a private agent also 404s. `message/*` additionally runs the
caller's outbound `a2aTargets` and the target's `a2aInbound` + per-caller rate
limit. Task reads/cancels skip the policy evaluation, so polling does not burn
the target's invoke budget. They are safe because **a task is bound to the caller
principal that created it**: tasks/get|cancel|resubscribe answers TaskNotFound
unless the stored caller equals this caller. The exception is a human/API key of the
agent's own tenant (the owner). An agent caller's tasks are bound to its SPIFFE id,
so a human of the same caller tenant cannot read them. Budgets are checked
before a task starts (hard-fail → error).

**Replay.** The same caller re-sending the same `messageId` to the same agent gets
the existing task back instead of a second run. This is read-then-insert, so two
truly concurrent duplicates can still create two runs (named ceiling).

### Outbound: `a2a_call` built-in tool

A built-in tool for the tool loop and workflow `tool` nodes:
`{agentUrl, message}` → fetch the card → JSON-RPC `message/send` (blocking) →
poll `tasks/get` ≤ 60 s → return the text. Gates, all required:

1. an agent principal is acting (no identity → refused);
2. policy `tools` contains `a2a_call` (the generic tool gate);
3. policy `a2aTargets` lists the remote base URL (exact or glob, e.g.
   `https://agents.example.com/*`). The tool is advertised to the model **only**
   when the policy names an explicit http(s) target. Legacy-permissive `*`
   does not count;
4. policy `egressHosts` covers the host;
5. **card spoofing**: the card's own `url` is self-asserted, so it must pass
   3 and 4 again before any message is sent;
6. **SSRF**: every request uses the callbackUrl client (resolved IPs checked
   against private/loopback/metadata ranges, dial pinned, redirects refused, https
   in prod), plus 1 MiB response and 60 s caps. `PAL_A2A_ALLOW_PRIVATE=1` lets
   dev/test reach loopback and is ignored in prod.

**Remote content is data.** The result is returned as a tool result, fenced
(`<<<remote-agent-content>>>`; any `<<<` inside is defanged so the fence cannot be
closed from within), truncated to 16 KiB and labelled `UNTRUSTED`. It is never
placed in a system prompt. The contact reply path drops the tool (not a read verb).
The A2A `messageId` is derived from (run, endpoint, message) so a retry or
crash-replay is the same message (invariant #8). A PAL remote dedups it.

Outbound credentials (calling a remote that requires auth) are a follow-up. The
first cut reaches remotes that accept unauthenticated calls or are fronted by an
egress-broker injection rule.

### Fixed alongside

The inline executor's `running`/`succeeded`/`failed` writes overwrote a
`cancelled` run, so `/v1/runs/{id}/cancel` (and tasks/cancel) reported a cancel
that did not hold. Every such write now carries `AND status <> 'cancelled'`.

## Threat model

| Threat | Control |
| --- | --- |
| Card spoofing (a remote card points its `url` at an internal or unlisted host) | Card `url` re-checked against a2aTargets + egressHosts + SSRF before sending |
| Cross-tenant / cross-caller task access | Tasks bound to the creating principal; other callers get -32001; private agents 404 at the transport |
| SSRF via outbound client | Pinned-IP client, private/metadata ranges blocked, no redirects, https in prod, size/time caps |
| Prompt injection from remote agents | Fenced, defanged, truncated tool result marked UNTRUSTED; never in a system prompt; tool absent on the contact path |
| Replay | Deterministic outbound messageId; inbound per-caller messageId dedup; agent tokens are short-lived and audience-bound (ADR 0055) |
| Inbound abuse | a2aInbound policy + per-caller per-minute limit + budgets, all on message/* |

## Verification

The A2A TCK `0.3.0.beta6` (mandatory: 28 pass / 2 fail / 3 skip) and the
reference `a2a-sdk==0.3.26` client (card, send, stream, get, cancel) were run
against PAL. PAL's `a2a_call` was run against an `a2a-sdk==0.3.26` sample server.
All of these failures are multi-turn continuation (above). The exact commands
are in the PR.
